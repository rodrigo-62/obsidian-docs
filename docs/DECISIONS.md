# Decisions log

Decisions made autonomously where the spec said "confirm with me", "stop and ask", or left a gap. Newest at the bottom of each phase. ⚠ marks the ones most worth reviewing.

## Phase 0: setup and research

- **D0.1 ⚠ Build from scratch, don't fork.** Document Comments is the closest match, but its body format is linear and line-based and sits between paragraphs. The spec wants a tree, Markdown bodies, and one block at the end of the file. A fork would mean rewriting its parser, writer, cards and margin, and inheriting about 9k lines of features v1 doesn't need. Its ideas are reused instead (see `docs/RESEARCH.md`).
- **D0.2 ⚠ Storage format: §5.3 as written, plus three refinements.** (a) A U+200B "guard" before any marker that starts a non-heading line's text, because otherwise CommonMark turns the line into a raw HTML block and Reading view loses all formatting there (Document Comments hit this too). (b) `-->` and `--!>` inside the JSON are written as `--\u003e` / `--!\u003e` instead of `--\>`, since `\>` is invalid JSON while `\u003e` is decoded by `JSON.parse` for free. (c) Anchor markers use exactly Document Comments' syntax `<!--c:ID-->…<!--/c:ID-->`.
- **D0.3 Zoom stays font-scaling (§4.2).** Note Zoom uses CSS `zoom` without any CodeMirror coordinate handling. That is the risk the spec names, and it would also skew the margin card positions. No reason to reconsider.
- **D0.4 Tooling.** nixpkgs-unstable flake with `nodejs_22`. Current versions: esbuild 0.28 (vitest 5 needs ≥0.27; the template pins 0.25), TypeScript 7, `obsidian` 1.14.4 typings, `@codemirror/state`/`view` pinned to the versions `obsidian` declares as peers. ESLint from the template was not carried over, to keep the toolchain small. The build is `tsc --noEmit` plus esbuild.
- **D0.5 Build output.** esbuild writes `dist/main.js` and `dist/styles.css` (CSS is bundled from `src/styles/index.css`). An `onEnd` hook copies them and `manifest.json` into `test-vault/.obsidian/plugins/folio/` and drops a `.hotreload` marker there. No symlinks, so it works the same everywhere.
- **D0.6 Test vault is generated.** The sample notes live in `scripts/vault-src/` and are written by `npm run vault:reset` (`scripts/build-test-vault.mjs`). That script refuses to write outside `test-vault/` and never touches `.obsidian/`. It also generates the ~13k-word, 100-thread performance note and a small PNG. The vault notes are committed too, so a clone works without running it.
- **D0.7 Hot Reload** 0.3.1 is copied from pjeby/hot-reload into the test vault, and both plugins are listed in `community-plugins.json`. The core *Footnotes* plugin is enabled in the test vault.
- **D0.8 License** is left `UNLICENSED`/private in `package.json`. Pick one before publishing.

## Phase 2: comment core

- **D2.1 Thread JSON layout.** Thread fields go one per line and **each comment on a single line** (as in the spec's example), so adding a reply is a one-line git diff. Key order is fixed (`quote, created, resolved, resolvedAt, comments`; `id, parent, created, edited, body`). Unknown keys are preserved, for forward compatibility.
- **D2.2 ⚠ A damaged thread block is read-only.** If the JSON doesn't parse, Folio refuses every comment write for that note (with a notice) and shows the block instead of hiding it, so you can fix it by hand. It never overwrites data it couldn't read.
- **D2.3 Range placement on create.** Selections are trimmed of surrounding whitespace. They are moved past block markup (`- `, `> `, `1. `, `- [ ] `, `#`, callouts, footnote labels), never end at the start of a line, and widen to whole inline code spans. They are **refused** if they start or end inside fenced code or the frontmatter. A range that fully contains a code block is fine.
- **D2.4 Typing at a range edge goes outside the range** (Google Docs behaviour), at the start as well as the end. Within a run of adjacent markers, the insertion goes to the position covered by the fewest ranges.
- **D2.5 Deleting.** A marker is only deleted together with its partner. A deletion that would remove one marker of a pair is split around that marker, which then survives at the deletion point. If a deletion would hit *only* hidden markers (e.g. Backspace right after a start marker), it moves one character past them instead. A pair left with no text between its markers is removed in the same edit, and its thread becomes detached.
- **D2.6 Stray markers.** Lone, reversed, duplicate, or with no thread: they are hidden and ignored while reading. They are removed only as part of a comment write (or the *Repair* command), never just by opening a note, so opening never causes git or Sync churn.
- **D2.7 ⚠ Paste.** Pasted markers are **stripped**, except a single complete pair whose thread exists in this note but is currently detached (pasting restores its anchor). This is the "de-duplicate IDs" safety net. Renaming pasted IDs would create highlight pairs with no thread data.
- **D2.8 Deleting a reply** re-attaches its replies to its parent, so no branch disappears. Deleting the root comment deletes the thread (with a confirmation, in the UI).
- **D2.9 IDs.** Thread IDs are 4 random base-36 characters that always start with a letter, unique against both thread keys and any marker in the file. Comment IDs are `a1, a2, …` per thread (max + 1).

## Phase 3: copy for LLM

- **D3.1 Output shape follows the spec's example.** `<document title>` (with `<notation>` inside), then `<footnotes>`, then `<comments>`. Notation lines appear only for features actually present (milestones, highlights, footnotes, embeds, images, private comments, detached threads), so a plain note exports as just `<document>…</document>`.
- **D3.2 ⚠ Footnote numbering.** Numeric labels and inline `^[…]` footnotes are renumbered 1…n in order of first reference, which matches what Obsidian's reading view shows. Named labels (`[^note]`) are kept. Definitions are listed in reference order. Multi-paragraph definitions keep their 4-space continuation indent.
- **D3.3 Threads.** Comment IDs in the export are `cN.k` (k = position in time order). `reply-to` appears only when the parent isn't the comment directly above. A multi-line anchor becomes an `<anchor>` child element instead of an attribute. Detached threads come last, with `detached="true"` and the cached quote. Attribute values escape `& " <`. In bodies, only closing tags like `</comment` are escaped (`<\/comment`), to keep bodies readable.
- **D3.4 Dates** are in **local time** (`YYYY-MM-DD HH:mm`) in the plugin. The pure function defaults to UTC, so tests are deterministic.
- **D3.5 Embeds.** `![[note]]`, `![[note#Heading]]` and `![[note#^block]]` are inlined as `<embed source="…">`, cleaned of the embedded note's frontmatter, markers, thread block and private comments. Embeds nested inside become `[embed: …]` references (depth 1, so cycles can't happen). Missing targets become `[embed: X (not found)]`. Images become `[image: file — alt]` (a pure size like `|300` is not treated as alt text). Other files become `[embedded file: name]`.
- **D3.6 Frontmatter** is kept minus the `folio`/`folio-*` keys, and dropped entirely if nothing remains. Selection exports leave it out.
- **D3.7 Commands and hotkeys.** *Copy for LLM* gets `Mod+Alt+C` by default. There are separate commands for the options modal, selection only, including resolved, comments only and text only. The editor context menu has *Copy for LLM* and, when text is selected, *Copy selection for LLM*. A header button (clipboard icon) appears on every note, controlled by a setting. The doc-mode toolbar adds the same button in Phase 1.
- **D3.8 What gets exported** is the editor's current text (`view.getViewData()`), including unsaved edits. Defaults come from the plugin settings (include resolved: off, embeds: inline, private: off).
- **D3.9** `minAppVersion` is 1.8.0 (it uses `Modal.setTitle` and the current `addAction`). You run 1.15.1.

## Phase 4: editor integration

- **D4.1 Full re-parse per document change.** `inlineCommentStore.read` takes about 1 ms on the 190k-character, 100-thread note (measured), so the StateField re-parses instead of mapping positions incrementally. That makes the code simpler and less error-prone. Thread objects are reused while the JSON block text is unchanged.
- **D4.2 Markers hidden in both Live Preview and Source mode** (replace decorations plus `atomicRanges`). The raw markers are only visible if you open the file elsewhere.
- **D4.3 ⚠ What is hidden at the end.** The hidden range is `"\n<!--folio:threads…-->"` to the end of the file. The blank line *before* the block stays visible as an empty last line, so pressing Enter or typing at the end of the note behaves normally. Text typed after the block is moved in front of it. Deletions can't reach into it (Select all + Delete keeps the block and detaches all threads, and Undo brings everything back). A missing blank line before the block is restored on the next comment write.
- **D4.4 Undo.** Comment writes are ordinary editor transactions, so **Ctrl+Z in the editor also undoes comment actions** (create, reply, resolve…), in order. This is deliberate. Keeping thread-block edits out of the history would let a later undo replay a stale block and corrupt the JSON.
- **D4.5 Copy/cut** strip markers (and the hidden block) only when the selection touches one. Otherwise the default handler runs.
- **D4.6 IME safety.** While composing (`input.type.compose`), insertion positions are not moved.
- **D4.7 No selection.** *Add comment* with an empty selection comments on the word at the cursor (Google Docs does the same).
- **D4.8 Activation.** Moving the cursor (click or keyboard) into commented text activates its innermost thread. Leaving it deactivates.
- **D4.9 Orphan quotes** are refreshed on every comment write, not at the moment the text is deleted. A thread orphaned by deleting edited text keeps the quote from its last write. Updating the quote mid-edit would mean rewriting the thread block on ordinary keystrokes.
- **D4.10 Interim composer.** Until the margin exists (Phase 5), *Add comment* opens a small modal (Ctrl+Enter saves, Esc cancels, empty = nothing). The modal stays as the fallback when there is no room for the margin.

## Phase 5: margin cards

- **D5.1 Margin layer** is a child of `.cm-scroller` (like CodeMirror's own layers), so cards scroll with the text for free. Positions are only recomputed in `requestMeasure` after document, geometry, viewport or height changes, or a card resize. Cards are placed with `transform: translateY()`. Anchors outside the viewport use `lineBlockAt` (height-map estimates, which settle as you scroll). Visible ones use `coordsAtPos`.
- **D5.2 Making room.** When a note has comments (or a draft), the editor gets `folio-has-margin`, which adds right padding (margin width + 40 px) to the scroller. The column then sits right of the text; with readable line width on, the text moves left a bit, as in Google Docs.
- **D5.3 ⚠ Compact inactive cards.** An inactive card shows the first comment (max 4 lines) and the latest reply, with "N more replies" between. The active card shows everything plus the reply box. This keeps 100 threads manageable in a 300 px column.
- **D5.4 Layout algorithm** is pure (`core/layout.ts`, tested): top-down stacking, and the active card (or a draft) is pinned to its anchor while earlier cards are pushed up. Cards never go above the first line. Detached threads stack below the end of the text under "Detached comments (N)".
- **D5.5 Replying.** The reply box replies to the last comment by default, so a plain conversation needs no chips. The ↩ icon on a comment (or "Reply to the first comment" in the ⋯ menu) targets that comment and shows "Replying to …" with an ×.
- **D5.6 Root comment actions** (edit, delete thread, reply to it) are in the card's ⋯ menu. Replies have hover icons. Deleting a reply needs no confirmation (Ctrl+Z in the editor undoes it). Deleting a thread asks first.
- **D5.7 Narrow panes.** When the scroller can't fit 380 px of text plus the margin, the margin hides and a "💬 N" pill appears top-right. Clicking it opens the **Comments sidebar** (also available as a command, any time). *Add comment* then uses the modal composer. The sidebar always follows the last active note.
- **D5.8 Empty drafts vanish** when focus leaves them, as in Google Docs. A draft with text stays until saved or cancelled.
- **D5.9 Tree view state** (per thread) is kept for the session only, keyed by file and thread. The default comes from settings (flat). It isn't written to the note.
- **D5.10 Testing without Obsidian.** `tests/margin.dom.test.ts` runs the real margin and cards in happy-dom against a CodeMirror view, with a minimal `obsidian` mock (`tests/mocks/obsidian.ts`, aliased in `vitest.config.ts`). Layout numbers are zero there, so positions still need the manual check.

## Phase 6: tree view and polish

- **D6.1 Tree view** (built in Phase 5): a per-card toggle (branch icon, or ⋯ → *Show as tree*). Indentation is capped at 2 levels. Deeper replies get a "↳ re:" chip so the parent stays clear. Branches collapse with ▾/▸. The setting *Thread display* picks the default.
- **D6.2 Keyboard navigation.** *Go to next comment* (`Mod+Alt+.`) and *Go to previous comment* (`Mod+Alt+,`) select the next or previous visible thread's text, wrapping around, and activate its card. *Reply to the active comment* focuses the reply box (margin, or sidebar when narrow). *Resolve the active comment* has no default hotkey. Ctrl+Alt+arrow keys were avoided because GNOME and other desktops use them to switch workspaces.
- **D6.3 ⚠ Reading view (basic).** Highlights are added by a Markdown post-processor. Obsidian removes HTML comments when rendering, so the commented text is found by comparing letters and digits of the source and the rendered section (`core/readingMatch.ts`), choosing the right occurrence when text repeats. Clicking a highlight opens the Comments sidebar on that thread. There are **no margin cards in Reading view**: the sidebar is the comment UI there, and replies, resolve and edit go through the note's (hidden) editor. Highlights can be missed where rendering changes the text a lot (e.g. an anchor that spans a footnote reference or a whole table).
- **D6.4** Changing the margin width or *show resolved* in settings applies to open notes immediately.

## Phase 1: doc mode and page appearance (done last, as asked)

- **D1.1 Where styles go.** Classes (`folio-doc`, `folio-theme-light|dark`) and variables are set on the MarkdownView's **content element** (`.view-content`), never on `body`. So the view header keeps the app theme, two panes with different notes differ, and the same note in two panes matches (both read the same frontmatter). Re-applied on `active-leaf-change`, `layout-change`, `file-open` and `metadataCache 'changed'`. Removed on unload and when doc mode is turned off.
- **D1.2 Zoom = font scaling (§4.2).** Text size = `folio-font-size` pt × 4/3 × zoom. Page width = `folio-width` em × that size, computed in JS as px and set as `--folio-page-width` and `--file-line-width`. `--font-preferred-size` is overridden directly (`--font-text-size` would have no effect, see RESEARCH). CSS `zoom` and `transform` are not used.
- **D1.3 Page look.** The editor's `.cm-sizer` (and the reading view's `.markdown-preview-sizer`) becomes the page: centred, page background, soft shadow, padding of 3 em top and 3.5 em sides (scaling with zoom), on a `--folio-surround` background. In doc mode the width applies whether or not Obsidian's "Readable line length" is on.
- **D1.4 ⚠ Default font size is 12 pt** (= Obsidian's 16 px), not Google Docs' 11 pt, so turning doc mode on doesn't shrink the text. Default width 42 em, zoom 100 %, theme *follow the app*, font *app font*. All are changeable in settings.
- **D1.5 ⚠ Paper palettes.** `src/styles/palette.css` is generated by `scripts/gen-palette.mjs` from Obsidian 1.15.1's `app.css`. For each page theme it re-declares Obsidian's ~236 body-level colour mappings plus that theme's base colours, with a white or near-black page and a grey surround. That makes the page theme independent of the app theme and of community themes that only scope variables to `body.theme-dark` (which the `theme-dark`-class trick would miss). If a future Obsidian version adds variables, re-run the script. Highlight colours also follow the page theme.
- **D1.6 Toolbar** (doc mode only, top of the view, wraps on narrow panes): zoom dropdown (50–200 % presets plus the current value), font picker, size −/value/+ (±1 pt; click the value to type one), width presets plus *Custom…*, a theme button cycling app → light → dark, add comment, show resolved, comments sidebar, and a **Copy for LLM** button (right-click for the options modal).
- **D1.7 Font picker.** A curated list of serif, sans and mono fonts (free ones first), plus *Custom font name…* and *List installed fonts…*, which uses `window.queryLocalFonts()` if Electron allows it and otherwise falls back to typing a name. Missing fonts show "(not installed)", detected by measuring text width (`document.fonts.check` returns true for missing fonts). Times New Roman, Arial and Georgia show metric-compatible free alternatives in a tooltip.
- **D1.8 Instant feedback.** Toolbar, commands and Ctrl+Alt+scroll apply the change to the view immediately, then write the frontmatter with `processFrontMatter` (debounced 300–500 ms for repeated zoom or size steps), so a burst of zoom steps doesn't rewrite the file repeatedly.
- **D1.9 Toggle doc mode** adds or removes only `folio: true`. The other `folio-*` keys are kept, so turning it back on restores the look. *Reset zoom* removes `folio-zoom` (back to the plugin default).
- **D1.10 Commands:** toggle doc mode, zoom in, zoom out, reset zoom, font size bigger and smaller, change page theme. None has a default hotkey except the existing Ctrl+Alt+C, Ctrl+Alt+M, Ctrl+Alt+. and Ctrl+Alt+,.
