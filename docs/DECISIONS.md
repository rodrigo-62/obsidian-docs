# Decisions log

Decisions made autonomously where the spec said "confirm with me", "stop and ask", or left a gap. Newest at the bottom of each phase. ⚠ marks the ones most worth reviewing.

## Phase 0: setup and research

- **D0.1 ⚠ Build from scratch, don't fork.** Document Comments is the closest match, but its body format is linear and line-based and sits between paragraphs. The spec wants a tree, Markdown bodies, and one block at the end of the file. A fork would mean rewriting its parser, writer, cards and margin, and inheriting about 9k lines of features v1 doesn't need. Its ideas are reused instead (see `docs/RESEARCH.md`).
- **D0.2 ⚠ Storage format: §5.3 as written, plus three refinements.** (a) A U+200B "guard" before any marker that starts a non-heading line's text, because otherwise CommonMark turns the line into a raw HTML block and Reading view loses all formatting there (Document Comments hit this too). (b) `-->` and `--!>` inside the JSON are written as `--\u003e` / `--!\u003e` instead of `--\>`, since `\>` is invalid JSON while `\u003e` is decoded by `JSON.parse` for free. (c) Anchor markers use exactly Document Comments' syntax `<!--c:ID-->…<!--/c:ID-->`.
- **D0.3 Zoom stays font-scaling (§4.2).** Note Zoom uses CSS `zoom` without any CodeMirror coordinate handling. That is the risk the spec names, and it would also skew the margin card positions. No reason to reconsider.
- **D0.4 Tooling.** nixpkgs-unstable flake with `nodejs_22`. Current versions: esbuild 0.28 (vitest 5 needs ≥0.27; the template pins 0.25), TypeScript 7, `obsidian` 1.14.4 typings, `@codemirror/state`/`view` pinned to the versions `obsidian` declares as peers. ESLint from the template was not carried over, to keep the toolchain small. The build is `tsc --noEmit` plus esbuild.
- **D0.5 Build output.** esbuild writes `dist/main.js` and `dist/styles.css` (CSS is bundled from `src/styles/index.css`). An `onEnd` hook copies them and `manifest.json` into `test-vault/.obsidian/plugins/folio/` and drops a `.hotreload` marker there. No symlinks, so it works the same everywhere.
- **D0.6 Test vault is generated.** The sample notes live in `scripts/vault-src/` and are written by `npm run vault:reset` (`scripts/build-test-vault.mjs`). That script refuses to write outside `test-vault/` and never touches `.obsidian/`. It also generates the ~13k-word, 100-thread performance note and a small PNG. The vault notes are committed too, so a clone works without running it.
- **D0.7 Hot Reload** 0.3.1 is copied from pjeby/hot-reload into the test vault, and both plugins are listed in `community-plugins.json`. The core *Footnotes* plugin is enabled in the test vault.
- **D0.8 License:** MIT (`LICENSE`, added by the user; `package.json` says `MIT`). `private: true` stays in `package.json`; it only blocks publishing to npm, which Obsidian plugins don't use.

## Phase 2: comment core

- **D2.1 Thread JSON layout.** Thread fields go one per line and **each comment on a single line** (as in the spec's example), so adding a reply is a one-line git diff. Key order is fixed (`quote, created, resolved, resolvedAt, comments`; `id, parent, created, edited, body`). Unknown keys are preserved, for forward compatibility.
- **D2.2 ⚠ A damaged thread block is read-only.** If the JSON doesn't parse, Folio refuses every comment write for that note (with a notice) and shows the block instead of hiding it, so you can fix it by hand. It never overwrites data it couldn't read.
- **D2.3 Range placement on create.** Selections are trimmed of surrounding whitespace. They are moved past block markup (`- `, `> `, `1. `, `- [ ] `, `#`, callouts, footnote labels), never end at the start of a line, and widen to whole inline code spans. They are **refused** if they start or end inside fenced code or the frontmatter. A range that fully contains a code block is fine.
- **D2.4 Typing at a range edge goes outside the range** (Google Docs behaviour), at the start as well as the end. Within a run of adjacent markers, the insertion goes to the position covered by the fewest ranges.
- **D2.5 Deleting.** A marker is only deleted together with its partner. A deletion that would remove one marker of a pair is split around that marker, which then survives at the deletion point. If a deletion would hit *only* hidden markers (e.g. Backspace right after a start marker), it moves one character past them instead. A pair left with no text between its markers is removed in the same edit, and its thread becomes detached.
- **D2.6 Stray markers.** Lone, reversed, duplicate, or with no thread: they are hidden and ignored while reading. They are removed only as part of a comment write (or the *Repair* command), never just by opening a note, so opening never causes git or Sync churn.
- **D2.7 ⚠ Paste.** Pasted markers are **stripped**, except a single complete pair whose thread exists in this note but is currently detached (pasting restores its anchor). This is the "de-duplicate IDs" safety net. Renaming pasted IDs would create highlight pairs with no thread data.
- **D2.8 Deleting a reply** re-attaches its replies to its parent, so no branch disappears. Deleting the root comment deletes the thread (with a confirmation, in the UI).
- **D2.9 IDs.** Thread IDs are 4 random base-36 characters that always start with a letter, unique against both thread keys and any marker in the file. Comment IDs are `a1, a2, …` per thread (max + 1).

## Phase 3: copy for LLM

- **D3.1 Output shape follows the spec's example.** `<document title>` (with `<notation>` inside), then `<footnotes>`, then `<comments>`. Notation lines appear only for features actually present (milestones, highlights, footnotes, embeds, images, private comments, detached threads), so a plain note exports as just `<document>…</document>`.
- **D3.2 ⚠ Footnote numbering.** Numeric labels and inline `^[…]` footnotes are renumbered 1…n in order of first reference, which matches what Obsidian's reading view shows. Named labels (`[^note]`) are kept. Definitions are listed in reference order. Multi-paragraph definitions keep their 4-space continuation indent.
- **D3.3 Threads.** Comment IDs in the export are `cN.k` (k = position in time order). `reply-to` appears only when the parent isn't the comment directly above. A multi-line anchor becomes an `<anchor>` child element instead of an attribute. Detached threads come last, with `detached="true"` and the cached quote. Attribute values escape `& " <`. In bodies, only closing tags like `</comment` are escaped (`<\/comment`), to keep bodies readable.
- **D3.4 Dates** are in **local time** (`YYYY-MM-DD HH:mm`) in the plugin. The pure function defaults to UTC, so tests are deterministic.
- **D3.5 Embeds.** `![[note]]`, `![[note#Heading]]` and `![[note#^block]]` are inlined as `<embed source="…">`, cleaned of the embedded note's frontmatter, markers, thread block and private comments. Embeds nested inside become `[embed: …]` references (depth 1, so cycles can't happen). Missing targets become `[embed: X (not found)]`. Images become `[image: file — alt]` (a pure size like `|300` is not treated as alt text). Other files become `[embedded file: name]`.
- **D3.6 Frontmatter** is kept minus the `folio`/`folio-*` keys, and dropped entirely if nothing remains. Selection exports leave it out.
- **D3.7 Commands and hotkeys.** *Copy for LLM* gets `Mod+Alt+C` by default. There are separate commands for the options modal, selection only, including resolved, comments only and text only. The editor context menu has *Copy for LLM* and, when text is selected, *Copy selection for LLM*. A header button (clipboard icon) appears on every note, controlled by a setting. The doc-mode toolbar adds the same button in Phase 1.
- **D3.8 What gets exported** is the editor's current text (`view.getViewData()`), including unsaved edits. Defaults come from the plugin settings (include resolved: off, embeds: inline, private: off).
- **D3.9** `minAppVersion` is 1.8.0 (it uses `Modal.setTitle` and the current `addAction`). You run 1.15.1.

## Phase 4: editor integration

- **D4.1 Full re-parse per document change.** `inlineCommentStore.read` takes about 1 ms on the 190k-character, 100-thread note (measured), so the StateField re-parses instead of mapping positions incrementally. That makes the code simpler and less error-prone. Thread objects are reused while the JSON block text is unchanged.
- **D4.2 Markers hidden in both Live Preview and Source mode** (replace decorations plus `atomicRanges`). The raw markers are only visible if you open the file elsewhere.
- **D4.3 ⚠ What is hidden at the end.** The hidden range is `"\n<!--folio:threads…-->"` to the end of the file. The blank line *before* the block stays visible as an empty last line, so pressing Enter or typing at the end of the note behaves normally. Text typed after the block is moved in front of it. Deletions can't reach into it (Select all + Delete keeps the block and detaches all threads, and Undo brings everything back). A missing blank line before the block is restored on the next comment write.
- **D4.4 Undo.** Comment writes are ordinary editor transactions, so **Ctrl+Z in the editor also undoes comment actions** (create, reply, resolve…), in order. This is deliberate. Keeping thread-block edits out of the history would let a later undo replay a stale block and corrupt the JSON.
- **D4.5 Copy/cut** strip markers (and the hidden block) only when the selection touches one. Otherwise the default handler runs.
- **D4.6 IME safety.** While composing (`input.type.compose`), insertion positions are not moved.
- **D4.7 No selection.** *Add comment* with an empty selection comments on the word at the cursor (Google Docs does the same).
- **D4.8 Activation.** Moving the cursor (click or keyboard) into commented text activates its innermost thread. Leaving it deactivates.
- **D4.9 Orphan quotes** are refreshed on every comment write, not at the moment the text is deleted. A thread orphaned by deleting edited text keeps the quote from its last write. Updating the quote mid-edit would mean rewriting the thread block on ordinary keystrokes.
- **D4.10 Interim composer.** Until the margin exists (Phase 5), *Add comment* opens a small modal (Ctrl+Enter saves, Esc cancels, empty = nothing). The modal stays as the fallback when there is no room for the margin.

## Phase 5: margin cards

- **D5.1 Margin layer** is a child of `.cm-scroller` (like CodeMirror's own layers), so cards scroll with the text for free. Positions are only recomputed in `requestMeasure` after document, geometry, viewport or height changes, or a card resize. Cards are placed with `transform: translateY()`. Anchors outside the viewport use `lineBlockAt` (height-map estimates, which settle as you scroll). Visible ones use `coordsAtPos`.
- **D5.2 Making room.** When a note has comments (or a draft), the editor gets `folio-has-margin`, which adds right padding (margin width + 40 px) to the scroller. The column then sits right of the text; with readable line width on, the text moves left a bit, as in Google Docs.
- **D5.3 ⚠ Compact inactive cards.** An inactive card shows the first comment (max 4 lines) and the latest reply, with "N more replies" between. The active card shows everything plus the reply box. This keeps 100 threads manageable in a 300 px column.
- **D5.4 Layout algorithm** is pure (`core/layout.ts`, tested): top-down stacking, and the active card (or a draft) is pinned to its anchor while earlier cards are pushed up. Cards never go above the first line. Detached threads stack below the end of the text under "Detached comments (N)".
- **D5.5 Replying.** The reply box replies to the last comment by default, so a plain conversation needs no chips. The ↩ icon on a comment (or "Reply to the first comment" in the ⋯ menu) targets that comment and shows "Replying to …" with an ×.
- **D5.6 Root comment actions** (edit, delete thread, reply to it) are in the card's ⋯ menu. Replies have hover icons. Deleting a reply needs no confirmation (Ctrl+Z in the editor undoes it). Deleting a thread asks first.
- **D5.7 Narrow panes.** When the scroller can't fit 380 px of text plus the margin, the margin hides and a "💬 N" pill appears top-right. Clicking it opens the **Comments sidebar** (also available as a command, any time). *Add comment* then uses the modal composer. The sidebar always follows the last active note.
- **D5.8 Empty drafts vanish** when focus leaves them, as in Google Docs. A draft with text stays until saved or cancelled.
- **D5.9 Tree view state** (per thread) is kept for the session only, keyed by file and thread. The default comes from settings (flat). It isn't written to the note.
- **D5.10 Testing without Obsidian.** `tests/margin.dom.test.ts` runs the real margin and cards in happy-dom against a CodeMirror view, with a minimal `obsidian` mock (`tests/mocks/obsidian.ts`, aliased in `vitest.config.ts`). Layout numbers are zero there, so positions still need the manual check.

## Phase 6: tree view and polish

- **D6.1 Tree view** (built in Phase 5): a per-card toggle (branch icon, or ⋯ → *Show as tree*). Indentation is capped at 2 levels. Deeper replies get a "↳ re:" chip so the parent stays clear. Branches collapse with ▾/▸. The setting *Thread display* picks the default.
- **D6.2 Keyboard navigation.** *Go to next comment* (`Mod+Alt+.`) and *Go to previous comment* (`Mod+Alt+,`) select the next or previous visible thread's text, wrapping around, and activate its card. *Reply to the active comment* focuses the reply box (margin, or sidebar when narrow). *Resolve the active comment* has no default hotkey. Ctrl+Alt+arrow keys were avoided because GNOME and other desktops use them to switch workspaces.
- **D6.3 ⚠ Reading view (basic).** Highlights are added by a Markdown post-processor. Obsidian removes HTML comments when rendering, so the commented text is found by comparing letters and digits of the source and the rendered section (`core/readingMatch.ts`), choosing the right occurrence when text repeats. Clicking a highlight opens the Comments sidebar on that thread. There are **no margin cards in Reading view**: the sidebar is the comment UI there, and replies, resolve and edit go through the note's (hidden) editor. Highlights can be missed where rendering changes the text a lot (e.g. an anchor that spans a footnote reference or a whole table).
- **D6.4** Changing the margin width or *show resolved* in settings applies to open notes immediately.

## Phase 1: doc mode and page appearance (done last, as asked)

- **D1.1 Where styles go.** Classes (`folio-doc`, `folio-theme-light|dark`) and variables are set on the MarkdownView's **content element** (`.view-content`), never on `body`. So the view header keeps the app theme, two panes with different notes differ, and the same note in two panes matches (both read the same frontmatter). Re-applied on `active-leaf-change`, `layout-change`, `file-open` and `metadataCache 'changed'`. Removed on unload and when doc mode is turned off.
- **D1.2 Zoom = font scaling (§4.2).** Text size = `folio-font-size` pt × 4/3 × zoom. Page width = `folio-width` em × that size, computed in JS as px and set as `--folio-page-width` and `--file-line-width`. `--font-preferred-size` is overridden directly (`--font-text-size` would have no effect, see RESEARCH). CSS `zoom` and `transform` are not used.
- **D1.3 Page look.** The editor's `.cm-sizer` (and the reading view's `.markdown-preview-sizer`) becomes the page: centred, page background, soft shadow, padding of 3 em top and 3.5 em sides (scaling with zoom), on a `--folio-surround` background. In doc mode the width applies whether or not Obsidian's "Readable line length" is on.
- **D1.4 ⚠ Default font size is 12 pt** (= Obsidian's 16 px), not Google Docs' 11 pt, so turning doc mode on doesn't shrink the text. Default width 42 em, zoom 100 %, theme *follow the app*, font *app font*. All are changeable in settings.
- **D1.5 ⚠ Paper palettes.** `src/styles/palette.css` is generated by `scripts/gen-palette.mjs` from Obsidian 1.15.1's `app.css`. For each page theme it re-declares Obsidian's ~236 body-level colour mappings plus that theme's base colours, with a white or near-black page and a grey surround. That makes the page theme independent of the app theme and of community themes that only scope variables to `body.theme-dark` (which the `theme-dark`-class trick would miss). If a future Obsidian version adds variables, re-run the script. Highlight colours also follow the page theme.
- **D1.6 Toolbar** (doc mode only, top of the view, wraps on narrow panes): zoom dropdown (50–200 % presets plus the current value), font picker, size −/value/+ (±1 pt; click the value to type one), width presets plus *Custom…*, a theme button cycling app → light → dark, add comment, show resolved, comments sidebar, and a **Copy for LLM** button (right-click for the options modal).
- **D1.7 Font picker.** A curated list of serif, sans and mono fonts (free ones first), plus *Custom font name…* and *List installed fonts…*, which uses `window.queryLocalFonts()` if Electron allows it and otherwise falls back to typing a name. Missing fonts show "(not installed)", detected by measuring text width (`document.fonts.check` returns true for missing fonts). Times New Roman, Arial and Georgia show metric-compatible free alternatives in a tooltip.
- **D1.8 Instant feedback.** Toolbar, commands and Ctrl+Alt+scroll apply the change to the view immediately, then write the frontmatter with `processFrontMatter` (debounced 300–500 ms for repeated zoom or size steps), so a burst of zoom steps doesn't rewrite the file repeatedly.
- **D1.9 Toggle doc mode** adds or removes only `folio: true`. The other `folio-*` keys are kept, so turning it back on restores the look. *Reset zoom* removes `folio-zoom` (back to the plugin default).
- **D1.10 Commands:** toggle doc mode, zoom in, zoom out, reset zoom, font size bigger and smaller, change page theme. None has a default hotkey except the existing Ctrl+Alt+C, Ctrl+Alt+M, Ctrl+Alt+. and Ctrl+Alt+,.

## Feedback round 1 (after first manual test)

- **F1.1 Ctrl+Enter / Esc in comment boxes.** Obsidian's default hotkey for *Toggle checkbox status* is Mod+Enter, and Obsidian handles hotkeys before the text box sees the key. Every comment box now pushes an Obsidian keymap `Scope` while focused, with Mod+Enter → send and Esc → cancel.
- **F1.2 ⚠ A plain reply answers the thread** (its first comment), not the latest comment. The old default turned every plain reply into a deeper level in tree view (a staircase). A reply to a *specific* comment is made with that comment's ↩ button. Flat view shows the "↳ re:" chip only for replies to a comment other than the first one, when that comment isn't directly above. This differs from SPEC §5.5's literal rule, which would put a chip on almost every plain reply. The export still writes exact `reply-to` attributes.
- **F1.3 Chip flash bug.** The parent-comment flash used the class `is-flashing`, which Obsidian also styles (forced highlight background plus `mix-blend-mode`). In dark themes that made the text invisible, and the class was never removed. Now it uses its own class, removed after the animation.
- **F1.4 No more jump to the top on *Add comment*.** The new comment's text box was focused before its card was positioned, so the browser scrolled the editor to the card's temporary position at the top. All composer focusing now uses `preventScroll`.
- **F1.5 Activation needs the cursor strictly inside** a highlight. A cursor at either edge doesn't activate it.
- **F1.6 Sidebar.** It now finds the active note by itself (on open, on note switch, and if its note was closed). It loads deferred sidebar tabs (Obsidian 1.7+) before using them, and shows an error message instead of a blank pane if something fails.
- **F1.7 Toolbar button renamed "Copy"** (tooltip: "Copy for LLM …"). The editor context menu and command palette keep "Copy for LLM", because there it sits next to the normal Copy.
- **F1.8 Footnotes: Ctrl+Alt+F.** Obsidian has no built-in insert-footnote command. One hotkey does three things depending on the cursor. In normal text it inserts the next `[^n]` and a `[^n]: ` definition after the last definition (or at the end of the text, always before the hidden comment data), with the cursor in it. On or right after a reference it jumps to its definition (creating one if missing). In a definition it jumps back to the reference you came from. So you can write a footnote and press Ctrl+Alt+F to return, and press it again to go back to the footnote. Mouse navigation was left to Reading view, which already has it.
- **F1.9 ⚠ Theme sliders and a sepia theme.** The page themes are now *paper light*, *sepia* and *paper dark*, each with four sliders in settings: page brightness, text brightness, surround contrast and warmth (sepia tint). They apply live, and each theme has a reset. The whole Obsidian grey scale is remapped between the chosen page and text lightness, so muted text, borders and code backgrounds follow (`core/paperPalette.ts`). The theme button cycles app → light → sepia → dark.
- **F1.10 Page edges.** The light surround is now 12 points darker than the page (it was nearly white). The page has a thin border, and the follow-the-app theme also gets a darker surround.
- **F1.11 Smaller UI fixes.** The font menu has larger text. The idle "Reply…" box is one line and vertically centred, with no scrollbar. Cancel (button or Esc) clears the box and leaves it. The tree view's ▾/▸ toggle sits in the comment's date line instead of on its own line.

## Feedback round 2

- **F2.1 Sidebar root cause.** `CommentsSidebarView` declared fields named `headerEl` and `titleEl`. Those are Obsidian `ItemView` properties for the panel header, and Obsidian calls `this.titleEl.setText(…)` while opening the view. My `titleEl = null` field overwrote it, so opening the sidebar threw *before* any of my code ran ("Failed to open view"). The fields are renamed (`sb…`). The test mock's `ItemView` now has these properties and a `load()` that uses them, so this kind of shadowing fails the tests.
- **F2.2 Real-Obsidian checks.** Found by running Obsidian itself headless on the test vault (`scripts/obsidian-headless.sh`, isolated profile in `.scratch/`, Xvfb, remote debugging) and driving it with `scripts/cdp.mjs` (evaluate JS, read console errors, take screenshots). The sidebar, the surround click and *New doc* were verified this way.
- **F2.3 Clicking outside the text deactivates the active comment**: the grey surround, the page margins, and the empty space between cards.
- **F2.4 New doc**: a command (*Create new doc*), a ribbon icon, and *New doc* in a folder's right-click menu. It creates `Untitled doc.md` (then `Untitled doc 1.md`, …) with `folio: true` in the new-note folder, opens it, and selects the title for renaming, like *New note*. It doesn't add a button to the file explorer's header row: there's no API for that, only DOM injection.
- **F2.5 Other vaults**: `npm run build && npm run install-plugin -- /path/to/vault` copies `main.js`, `styles.css` and `manifest.json` into `<vault>/.obsidian/plugins/folio/`. It doesn't enable anything and touches nothing else.

## Feedback round 3

- **F3.1 ⚠ Oversized caret on new empty lines.** Chromium draws the native caret on an empty line as tall as the whole line box, but on text only as tall as the letters. With generous line spacing it looked about twice the text size until you typed (measured in Obsidian 1.15.1 at line-height 2.2: empty line box 47 px, text 24 px). In doc mode, empty lines now get a text-sized line-height (1.2), with the difference added back as padding. Line heights are unchanged (verified: 32 px before and after at 1.5). This assumes the spacing comes from `--line-height-normal`; a theme that sets `.cm-line` line-height some other way may need a tweak.
- **F3.2 Doc-mode font size on older Obsidian.** Obsidian 1.10.3 sizes the editor from `--font-text-size`, while 1.15 uses `--font-preferred-size`. Both are now set, so doc-mode size and zoom also work on 1.8–1.12 (found by running 1.10.3 headless).
- **F3.3 Comment text size**: setting *Comment text size* (Default or 11–20 px), also as an **Aa** dropdown in the doc toolbar. Global, not per note. Everything inside cards scales with it (meta lines 0.85 em).
- **F3.4 Reply box reset** after sending (the box kept the height of the long text you'd just sent).
- **F3.5 ⚠ Activation.** A cursor (empty selection) inside a highlight activates its thread however it got there. Before, a click that also focused the editor was missed, because it came without a "select" event. A **non-empty selection never changes the active thread**, so dragging a selection into a highlight no longer activates it.
- **F3.6 ⚠ The active card always sits exactly at its anchor.** Earlier cards are pushed up even past the top of the note (off screen for the moment), instead of the whole stack being pushed down when there wasn't room. Without an active card nothing starts above the first line. The draft card is watched for size changes, so a growing new comment pushes neighbours away instead of covering them. Cards glide with a softer easing.
- **F3.7 Comment menu** on double-click or right-click on a comment: Reply to this comment, Edit, Copy text, Go to the commented text (centres it in the editor), Resolve or Re-open thread, Delete (comment, or thread with confirmation).
- **F3.8 Google-Docs-like focus.** Inactive cards are flat, tinted and borderless. The active card has the page colour, a lifted shadow, a soft highlight-coloured outline (also visible on black themes), and steps 16 px out towards the text. The idle reply field is pill-shaped.
- **F3.9 Heading navigation**: *Go to next heading* (`Mod+Alt+↓`) and *Go to previous heading* (`Mod+Alt+↑`) put the cursor at the start of the heading's text and scroll it near the top. Headings in code and the thread block are ignored. Rebind them if your desktop uses these keys (some use Ctrl+Alt+arrows to switch workspaces).
- **F3.10 Headless checks run against your Obsidian version.** `scripts/obsidian-headless.sh` now works on a fresh copy of the test vault (`.scratch/headless-vault`, plugin folder symlinked to the build), so it never shares files with an Obsidian you have open. `OBSIDIAN_ASAR=…` runs a given Obsidian build (a copy of the auto-updated 1.15.1 was used). F3.1, F3.5–F3.8 were measured or seen there.

## Feedback round 4

- **F4.1 Comment text size applies immediately.** The size variable was only written during a measure pass, which a setting change didn't trigger (hovering did). It's now set when the margin syncs, and a re-layout is scheduled.
- **F4.2 ⚠ Crisper card text.** Cards were placed with `transform: translateY()` plus `will-change`, which puts them on GPU layers where text renders slightly softer. They now use `top` (with a `top` transition), at a small layout cost per move.
- **F4.3 Dropdown arrows follow the page theme.** Obsidian picks the arrow SVG by `body.theme-dark`, so a light or sepia page inside a dark app had white arrows. Page-theme overrides use Obsidian's own two SVGs.
- **F4.4** The active card steps out 8 px (was 16). In dark page or app themes its outline is a pastel gold (`--folio-active-outline`).
- **F4.5 `npm run update-vaults`** builds, then installs into every vault in `.install-targets` (gitignored, one path per line), and adds a `.hotreload` marker so Hot Reload, if installed there, reloads Folio. Claude must never run it (CLAUDE.md).
- **F4.6 Headless testing fix.** The vault copy used to symlink the whole plugin folder, so it shared (and once changed) the test vault's `data.json`. Now only the three build files are linked.
- **F4.7** Dark-theme highlights are a bit stronger (normal 0.24, active 0.5 opacity). Card animations are about twice as fast (top 140 ms, step-out and shadow 100 ms, highlight 80 ms). Activation itself is instant; the half-second felt was the chained card animations.

## F5: rename to "Docs"

- **F5.1 Names.** Repo `obsidian-docs`. Plugin id `docs` (the id `folio` is taken in the community directory, and ids may not contain "obsidian"), plugin name **Docs**. Frontmatter keys are now `docs`, `docs-zoom`, `docs-width`, `docs-font`, `docs-font-size`, `docs-theme`, and the comment block is `<!--docs:threads`. Commands appear as "Docs: …".
- **F5.2 ⚠ Old notes keep working.** The old `folio*` keys and `<!--folio:threads` are still read, and new keys win when both exist. Any frontmatter write by the plugin moves old keys to new ones, and any comment write rewrites the block with the new opener. *Docs: Upgrade notes from the old Folio format* converts a whole vault at once (verified in Obsidian 1.15.1 on a copy of the test vault: 5 notes' keys and 6 blocks converted, comments intact).
- **F5.3 Install migration.** `install-plugin` and `update-vaults` install into `plugins/docs`. If `plugins/folio` holds *this* plugin (manifest id `folio`, author Rodrigo Monteiro), they copy its `data.json`, replace `folio` with `docs` in `community-plugins.json`, rename `folio:*` hotkeys in `hotkeys.json`, and delete the old folder, so both versions can never run at once. ## F8: search scopes

The user noticed that Ctrl+F counted words in comments ("1 / 20") but stepping through showed only a few. Obsidian's find bar searches the raw file, which includes the hidden thread block (every comment body, plus a copy of each commented passage in `quote`, plus JSON keys like `"resolved"`) and the comment markers.

- **F8.1 ⚠ Replace was unsafe.** Obsidian's find bar tags its edits with the user event `searchReplace`, which `editFilter` doesn't handle (it only handles typing, deleting and moving). So a Replace All of `true` with `false` flipped every thread's resolved state, and replacing `"`, `a1` or `c:` could break the threads JSON or the markers, all invisibly. `searchReplaceFilter` (`cm/filters.ts`) now drops any `searchReplace` change that touches a marker or the hidden block, and applies the rest. It uses only CodeMirror's public API.
- **F8.2 Ctrl+F searches only the visible text.** The count must match what you can step through, as in Google Docs, where Ctrl+F searches the body only. Showing comment matches while cycling was rejected: it would mean mapping offsets in escaped JSON to rendered cards, a mixed count, and unclear replace semantics, with no extension point in Obsidian's find bar. Obsidian's find bar takes its matches from `editor.searchCursor(query)`, which is internal (not in the API). `searchScope.ts` wraps that method on the editor class and skips matches in hidden ranges. Behaviour was read from Obsidian 1.15.1's app.js: case-insensitive, wraps around, Obsidian stops counting at 9999 matches. **Fail-safe:** if the method or its cursor doesn't have the expected shape, the cursor passes through unchanged. If anything throws, wrapping turns off for the session and search is Obsidian's own again (F8.1 still protects Replace). Unload restores the method. If another plugin wrapped it after us, our wrapper becomes a pass-through. Verified in Obsidian 1.15.1: on the sample essay, "keeper" counts 5 (was 7), "resolved", "Agreed" and "c:" count 0, and every step lands on visible text. Vault-wide search (Ctrl+Shift+F) is unchanged and still finds words in comments, which helps to find the note a comment is in.
- **F8.3 Comment search in the Comments sidebar.** A search box under the sidebar header filters threads to those with a comment body containing the text (plain text, case-insensitive, like the find bar; the anchored text is not searched, since Ctrl+F covers it). Matches are highlighted with the CSS Custom Highlight API, so the cards' DOM is untouched. The colour is `--text-highlight-bg` (older Obsidian) or `--highlight-background` (1.9+). Enter and Shift+Enter step through the matching threads: each one becomes active and its text is selected, while focus stays in the box. Esc clears the search. Resolved threads follow *Show resolved*; when they're hidden, the status line offers "N more in resolved threads". The new command *Docs: Search comments* opens the sidebar with the box focused, pre-filled with a short one-line editor selection. Header and search stay at the top while the list scrolls.
- **F8.4 Bug found on the way:** the sidebar only refreshed for changes in `lastMarkdown`, which can be unset (e.g. after the plugin reloads while the sidebar has focus), so the active card wasn't marked. It now compares with the editor the sidebar actually shows.

## F9: comment box keys, search focus, priority, menus

- **F9.1 ⚠ Formatting keys in the comment box no longer act on the note.** The box's keymap scope had Obsidian's app scope as its parent. Obsidian's hotkey manager is a catch-all handler on that scope, so any hotkey the box didn't handle ran its command, and editor commands act on the active note. Ctrl+B bolded the commented text instead of the comment. The scope now has no parent. Keys it doesn't handle go to the text box as usual (typing, Ctrl+Z, Ctrl+A, arrows), so Obsidian's own hotkeys (including Ctrl+P) don't fire while the box has focus, as in Obsidian's modals. Bold, italic, link, strikethrough, highlight and inline code format the comment (`core/textFormat.ts`). They use your own hotkeys for those editor commands when you've changed them: this reads Obsidian's internal hotkey manager, guarded, falling back to Ctrl+B, Ctrl+I and Ctrl+K. Edits go through `execCommand('insertText')`, the only way the box's undo history records them, so Ctrl+Z works. Lint warns that `execCommand` is deprecated (2 warnings, no errors), and that is accepted for working undo. Without it, the code falls back to `setRangeText`.
- **F9.2 Comment search steps through matches, not threads.** The count is "3 / 12 in 4 threads". Each step activates the match's thread and gives that match a strong orange highlight, separate from the yellow highlight on all matches. It scrolls the match itself to a third of the way down, both in the sidebar and in the margin card (cards can be much taller than the screen). Matches are found in the rendered comments of the sidebar and of the source note's margin. The sidebar is scrolled at once; the margin again after its card has animated into place (260 ms). While searching, the list gets extra space at the bottom so the last matches can scroll up too. The sidebar no longer re-scrolls to the active card on every refresh, only when the active thread changes, so a refresh can't jump back to a tall card's top. If the text matches only Markdown syntax, so there's nothing rendered to point at, Enter steps through threads as before.
- **F9.3 Priority per thread: Low, Normal (default), High, Critical.** It belongs to the thread (the issue raised), not to each reply. Four levels: one below normal for nits that can recede, and two above it, so "must fix" stays distinct from "important" without the false precision of a 5-point scale. It is stored as `"priority": "low" | "high" | "critical"` on the thread. **Normal is never stored**, so existing notes, and threads nobody rated, stay byte-for-byte the same. A missing or unknown value reads as normal and is kept until you choose another. Docs 1.0 and 1.1 keep unknown thread fields when they rewrite threads, so a note rated here and edited with an older version keeps its priorities (the older version just doesn't show them). How to set it: a priority chip ("⚑ Normal") in the new-comment box, and "Low / Normal / High / Critical priority" in the comment menus (right-click, double-click, ⋯). Display: a badge for non-normal priorities, and an orange (high) or red (critical) left edge on the card. Copy for LLM adds `priority="…"` to rated threads, with one notation line explaining it. Not done yet: filtering or sorting by priority (possible next step in the sidebar).
- **F9.4 One menu at a time.** Comment menus stop the click from bubbling (so the card doesn't also activate). That meant Obsidian never saw the next right-click that normally closes an open menu, so menus piled up. `menus.ts` closes the previous menu before showing a new one.
